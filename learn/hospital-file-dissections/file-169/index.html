Hospital file #169: 1,788,001 entries pair zero counts with claim statistics

Published November 13, 2026 · Source audit: 2026-10-07 22:25 PDT; attached-source audit confirmation, not fresh endpoint check

Stored audit of one hospital price file found 1,788,001 entries pairing count zero with populated allowed-amount statistics across 1,892,073 applicable entries. Historical, de-identified review; not a fresh endpoint check.

What the stored audit found

This is one of the largest and cleanest inverse-encoding examples in the inventory. The file is not merely large; the affected share is overwhelming. That makes it useful for showing how a template can repeat one field conflict at scale.

The October 7 audit found 1,788,001 exact-zero code-bearing percentage or algorithm entries with numeric median, p10 and p90. The applicable denominator is 1,892,073 payer entries, so 94.5% are affected. All 104,072 positive entries have complete stats.

The inverse pattern is not a few outliers. Nearly every applicable conditional zero publishes a full statistical distribution. That points to a repeatable generation path, though the finding does not identify or establish causation by a vendor from the file alone.

The note strings were not ignored. The audit reviewed all exact joint generic and payer-note combinations. Historical, no-contract and price-history language may deserve its own adequacy review, but it does not change the basic conflict between count 0 and claim-derived statistics.

The positive comparison is clean: 104,072 positive entries have complete stats. The file knows how to encode the positive path. The failure is limited to zero-count rows that still publish statistics.

What a correction team should do

  • Treat this as a template-level correction, not row-by-row editing.
  • Generate a before-and-after census by count bucket, note string and payer-plan group.
  • Blank all three stats where count 0 is confirmed, or correct the count if remittances exist.
  • Retest the full JSON body after the change, including strict UTF-8 and the exact affected-row census.
