How to Check Whether Your Hospital Machine-Readable File Is Compliant

Updated November 16, 2026

Short answer. Review four layers: public access, file parsing, CMS template validation, and reconciliation to the hospital's source records. Run the current file through the CMS validator using Data Dictionary v3.0, then investigate the output and verify the underlying data. A successful download, a parse pass and a validator pass answer different questions. None alone certifies full compliance. [1-4]

Four checks, four different conclusions

  1. Public access: can a person and an automated client reach the intended hospital file through the required publication routes?
  2. Parsing: do the downloaded bytes form usable CSV or JSON rather than an error page or incomplete transfer?
  3. CMS validation: does the file meet the selected template and data dictionary specifications?
  4. Source reconciliation: do the disclosed items, payers, plans, rates and remittance statistics match the hospital's applicable records?

Keep an outcome for each layer. "Downloaded successfully" is not "schema valid." "No validator errors" is not "every applicable negotiated charge is present." These distinctions determine who needs to fix the problem and what evidence closes it.

1. Capture the file the public actually receives

Start from the hospital's published Price Transparency route. Record the source page, selected hospital location, retrieval time, final download destination and file-declared update date. Preserve the downloaded artifact. A file extension or HTTP success status does not establish that the response contains the intended file.

Section 180.50 requires free access without an account, password or personal identifying information, including access for automated searches and direct downloads. It also requires a root TXT locator and a Price Transparency footer link. Check these separately from the file's contents. One unsuccessful client request needs investigation before it supports an allegation about the hospital. [1]

2. Parse the actual bytes before diagnosing a schema error

Use a CSV-aware or JSON-aware parser, not a spreadsheet view or a naive split on commas. A quoted description can contain a comma without creating a new column. An HTML error page returned at a URL ending in .csv is a different problem from genuine CSV that uses the wrong CMS layout.

The current CSV dictionary permits tall and wide layouts and requires comma-separated plaintext. It also specifies unique headers in rows 1 and 3. Use its current instructions: the v3.0 dictionary says inadvertent leading/trailing spaces and case changes in the situations it describes do not generate a deficiency. Do not convert an older blanket whitespace warning into a current failure rule. [2, 5]

3. Run the CMS validator against the applicable version

For a current 2026 review, select Data Dictionary v3.0 in the CMS online validator. Save the selected dictionary version, run time, errors, alerts and whether the run completed. CMS distinguishes errors from alerts: an alert can indicate a concern even when the file meets technical form-and-manner specifications. [3]

The online tool stops if it finds an error in CSV rows 1-3 or more than 250 errors. Correct the displayed problems and rerun; a stopped run is not a complete error inventory. CMS recommends the CLI for large files, but retain the actual version and settings used rather than assuming an output cap describes every defect. [3, 5]

4. Review conditional fields, not just blank-cell totals

  • Identity and scope. Match the hospital and locations to the file. Review the active Type 2 organizational NPIs covered by the dictionary's hospital/hospital-unit taxonomy criteria; a number appearing in the file does not establish that the full required inventory is present. [1, 2]
  • Attestation. Check the required statement and named CEO, president or designated senior official. The CSV dictionary accepts true or false technically, but says true is required to meet the attestation obligation. Parsing an accepted boolean is not the same as satisfying that obligation. [1, 2]
  • Charge relationships. Check the code/code-type pairings and the payer, plan and methodology associated with each negotiated charge. Where methodology is other, the dictionary requires an explanation in the applicable notes. [2]
  • Allowed amounts. For the applicable percentage/algorithm charges, review the count and 10th, median and 90th percentile allowed amounts. The 2026 fields replace the estimated allowed amount. The current FAQ explains the remittance data and lookback requirements; do not fill these fields with negotiated percentages or a hospital-wide average. [2, 4]

When zero counts and blank statistics can be correct

For the no-claims scenario described in the CMS FAQ, the hospital encodes count 0, leaves the three allowed-amount statistics blank, and explains the insufficient remittance history in the associated generic or payer-specific notes. CMS also says to exclude zero-dollar remittances from the count. A count of 0 is therefore not automatically an error, and blanks alone are not a reliable defect test. [4]

A useful review checks the relationship among count, statistics, applicable charge and explanation. Preserve the row context and denominator rather than reporting an unexplained total of empty cells.

5. Reconcile content and retain a closure record

Use the chargemaster, applicable payer contracts and amendments, remittance data, location inventory and responsible owners to test completeness and accuracy. A public-file review cannot independently establish that an undisclosed contract or plan does not exist. Mark that work as unverified when the source records are unavailable, rather than issuing an all-clear.

Suggested audit record, not an additional CMS template: artifact identifier; hospital/location scope; retrieval and declared update dates; test and dictionary version; completed/stopped status; exact finding and affected denominator; regulatory or dictionary reference; correction owner; replacement artifact; and post-publication readback.

Close a finding against the check that raised it. Restored access closes the observed access problem, not a missing-data question. A corrected export still needs to be checked after publication. The rule requires at least annual standard-charge updates; checking after regeneration or a relevant operational change is an operating recommendation, not a separate federal monthly audit mandate. [1]

Worked evidence, not a compliance certificate
